## 1. Цель и назначение

Разработать раздел **«Аналитические отчёты»** с табличными и графическими отчётами по данным госпрограмм:

- **специалист** создаёт формы отчётов, и они автоматически заполняются данными системы;
- **пользователь** просматривает опубликованные отчёты и настраивает их представление под себя.

Ожидаемый результат: сокращение времени подготовки аналитики по госпрограммам и единый источник отчётности.

## 2. Принципы реализации: обособленный модуль

Исходного кода АИС госпрограмм (АИС ГП) в распоряжении разработчика нет, поэтому:

1. Модуль создаётся **как самостоятельное веб-приложение**, а не как доработка существующей системы.
2. Разработка и приёмка ведутся **так, как если бы АИС ГП уже существовала**: считается, что в ней реализованы авторизация, пользователи, роли и заполнение исходных данных. Эти функции в модуль **не входят**.
3. Данные для отчётов модуль получает через слой доступа к данным, построенный **по существующей модели данных АИС ГП** (`Ugf.GovPrograms.DataLayer`: `GovernmentProgram`, `Subprogram`, `PlanKeyEvent`, `IndicatorValue`, `KBKFinancing` и др.).
4. Для разработки и тестирования предусматривается **тестовый контур**:
   - тестовая база в структуре модели АИС ГП с демонстрационными данными (госпрограммы, показатели, контрольные события, финансирование);
   - **заглушка авторизации**, имитирующая вход из АИС ГП: тестовые специалист и обычный пользователь, а также сценарий «неавторизованный пользователь».

## 3. Границы работ

**Входит в проект:**

- каталог отчётов и просмотр отчётов;
- конструктор форм отчётов (для роли «Специалист»);
- табличные и графические представления данных;
- персональная настройка представления (для роли «Пользователь»);
- разграничение доступа по ролям;
- русскоязычный интерфейс в стиле АИС ГП;
- тестовый контур (тестовые данные и заглушка авторизации).

**Не входит:**

- изменение АИС ГП, её авторизации, управления пользователями и ввода исходных данных;
- OAuth, ЕСИА и иные внешние механизмы аутентификации;
- журналирование действий пользователей;
- миграция и очистка исходных данных.

## 4. Пользователи и роли

### 4.1. Как роли устроены в АИС ГП сейчас

По модели данных:

- Пользователь представлен только идентификатором `USER_GUID`. Таблицы пользователей в модели нет, учётные записи хранятся вне её.
- Единственная сущность роли — `UserGovernmentProgramRole`: пользователь, госпрограмма и **название роли строкой** (`ROLENAME`). Роль назначается в разрезе госпрограммы, справочника ролей нет.
- Права выдаются и точечно: на ФЦП (`FCPRight`), подпрограммы (`SubprogramRight`), основные мероприятия (`SubprogramActionRight`), НПА (`NpaRight`), мероприятия (`MeasureRight`), ввод показателей (`IndicatorInputPermisson`). Организационная привязка — `FOIV`, `Department`, `PersonInfo`.
- Готового разделения «специалист / обычный пользователь» для отчётов в модели **нет**: его нужно ввести.

### 4.2. Роли модуля

Модуль вводит две роли. Считается, что они назначаются в АИС ГП (в тестовом контуре — в заглушке) и передаются в модуль вместе с авторизованным пользователем.

| Роль | Возможности |
|---|---|
| **Специалист** | Создаёт, редактирует, копирует, публикует, снимает с публикации и удаляет формы отчётов. Видит все формы, включая черновики. Имеет все права пользователя |
| **Пользователь** | Видит только опубликованные формы. Не создаёт и не меняет форму. Настраивает представление отчёта под себя (п. 5.4) |
| **Неавторизованный** | Доступ к отчётам запрещён |

Название роли специалиста (значение `ROLENAME`) — настраиваемый параметр модуля.

## 5. Доступ и аутентификация

- Отдельная авторизация для модуля **не требуется**: используется текущая сессия пользователя АИС ГП, повторный ввод логина и пароля при переходе в отчёты не запрашивается.
- Все контроллеры и API-методы защищены проверкой авторизации и роли **на стороне сервера** (скрытия пунктов меню недостаточно).
- Неавторизованный запрос перенаправляется на страницу входа АИС.
- Черновики форм недоступны пользователю ни в списке, ни по прямой ссылке.
- Внешние провайдеры (OAuth и аналоги) не используются.

### 5.1. Данные пользователя, получаемые от АИС ГП

Считается, что АИС ГП передаёт модулю следующие сведения об авторизованном пользователе:

| Поле | Тип | Пример | Значение |
|---|---|---|---|
| `sub` | GUID | `11111111-1111-1111-1111-111111111111` | Идентификатор пользователя (`USER_GUID` модели АИС ГП) |
| `name` | строка | `Иванов И. И.` | ФИО для вывода в шапке |
| `role` | строка, одна или несколько | `ReportSpecialist` / `ReportUser` | Роль в модуле. Нет ни одной из двух — доступа нет |

Если ролей две, действует роль специалиста. Значения `role` настраиваются (п. 4.2).

**Интерфейс в коде модуля.** Остальной код зависит только от абстракции:

```csharp
public interface ICurrentUser
{
    bool IsAuthenticated { get; }
    Guid? UserId { get; }
    string DisplayName { get; }
    bool IsSpecialist { get; }   // роль ReportSpecialist
    bool IsUser { get; }         // роль ReportUser или ReportSpecialist
}
```

**Поведение при ошибках:**

| Ситуация | Результат |
|---|---|
| Пользователь не определён (нет входа или сессия недействительна) | Страница: перенаправление на вход АИС (адрес в настройках). AJAX/API: 401 без перенаправления |
| Пользователь вошёл, но роли модуля нет | 403 и страница «Нет доступа» |
| Пользователь пытается изменить форму, не будучи специалистом | 403 |

**Тестовый контур.** Вместо АИС ГП работает заглушка:
- страница `/Dev/Login` задаёт текущего пользователя с полями из таблицы выше на выбор: «Тестовый специалист», «Тестовый пользователь», «Пользователь без роли»; кнопка «Выйти» сбрасывает пользователя (сценарий неавторизованного);
- заглушка включается настройкой и недоступна в рабочей конфигурации;
- тестовые пользователи (GUID, ФИО, роль) хранятся в конфигурации.

## 6. Функциональные требования

### 6.1. Каталог отчётов
- Список отчётов с поиском по названию отчета и группировкой по госпрограммам.
- Признак «опубликован / черновик». **Черновики форм отчётов видны только специалистам**, пользователь видит только опубликованные формы.

### 6.2. Конструктор форм (Специалист)
- Выбор источника данных из перечня (п. 7) и отчётного периода.
- Выбор измерений, показателей и агрегаций (сумма, количество, доля, среднее, мин./макс.).
- Структура таблицы: многоуровневые заголовки, группировка строк (направление → госпрограмма → структурный элемент), итоги и строка «Всего».
- Расчётные столбцы по формулам (например, «выполнено в срок / запланировано × 100 %»). Язык формул **ограничен**: начинается с «=», числа, `+ - * /`, скобки, ссылки на поля в фигурных скобках (`{план}`, `{факт}`), функция «значение с запасным» `ЕСЛИПУСТО({скорректированное}; {исходное})`. Другие конструкции отклоняются при сохранении. Деление на ноль даёт пустое значение, а не ошибку.
- Правила исключения строк (например, исключить КБК по виду расходов и ГРБС) как условия на источник.
- Цветовая индикация значений по порогам.
- Определение фильтров, доступных пользователю (период, ответственный исполнитель, статус и др.).
- Выбор типа визуализации и предпросмотр.
- Сохранение как черновик, публикация, копирование, снятие с публикации.

После публикации форма **заполняется данными системы автоматически** при каждом открытии: специалист задаёт правила, а не вводит числа.

### 6.3. Табличные и графические отчёты
- Таблицы: сортировка, иерархическая группировка со сворачиванием, итоги и подытоги, постраничная загрузка или виртуализация на больших объёмах.
- Диаграммы: столбчатые, линейные, круговые, с областями, накопительные (stacked) и нормированные.
- **Диаграмма Маримекко (вторая очередь)** — структура показателя по двум измерениям (например, ширина столбца — объём финансирования госпрограммы, сегменты — доли ГРБС).
- Подсказки при наведении, легенда с включением и отключением серий, переключение «таблица ↔ график» на одних данных.

> **Примечание по Маримекко.** В стандартной поставке Kendo UI Chart такого типа диаграммы нет. Реализация потребует кастомного решения (например, на Kendo Drawing API) либо дополнительной библиотеки. Это отдельный пункт оценки; способ реализации (Kendo Drawing API, поверхность canvas) описан в приложении А (`brief_appendix_marimekko.md`). По согласованию с заказчиком диаграмма Маримекко допустима во второй очереди и в первую версию не входит.

### 6.4. Настройка представления (Пользователь)
Пользователь **не меняет форму**, но настраивает отображение под себя:
- показывает, скрывает и переставляет столбцы;
- применяет фильтры из числа разрешённых специалистом;
- сортирует и меняет группировку в допустимых пределах;
- выбирает вид (таблица или график) среди доступных для формы;
- сохраняет настройки как личное представление и возвращается к исходному виду.

Личные настройки видны только самому пользователю.

## 7. Источники данных и примеры отчётов

Конкретные отчёты создаёт специалист в конструкторе, поэтому перечень отчётов не фиксируется и разработчиками не поставляется. Ниже — **иллюстративные примеры**, показывающие, какие данные модели должны быть доступны конструктору и какие возможности он должен поддерживать. Примеры взяты из печатных форм сводного годового доклада (СГД) из ВКР (в интерфейсе АИС ГП — «Приложение 2–10»). Их же можно использовать как тестовые сценарии.

| № | Отчёт | Сущности модели | Ключевые показатели | Вид |
|---|---|---|---|---|
| 1 | Выполнение контрольных событий по планам реализации ГП (прил. 2, 3) | `GovernmentProgram`, `PlanKeyEvent`, `ReportPlanKeyEvent`, `ProgramScope` | Запланировано КС; выполнено в срок, позже срока, не выполнено; доли в % | Таблица с группировкой по направлениям и ГП; накопительная столбчатая |
| 2 | Выполнение КС по детальным планам-графикам (прил. 4) | `PlanKeyEvent`, `ReportPlanKeyEvent`, `PlanSimpleAction` | Наступили в срок, позже срока, не наступили | Таблица; круговая |
| 3 | Значения показателей госпрограмм (план/факт, непилотные) | `Indicator`, `IndicatorValue`, `ReportIndicatorValue`, `Unit` | План, факт, отклонение, причины отклонения | Таблица; столбчатая «план/факт» |
| 4 | Кассовое исполнение госпрограмм (прил. 9) | `KBKFinancing`, `ReportKBKFinancing`, `KBK`, `GRBS`, `CashExecution` | Бюджетные ассигнования, кассовое исполнение, % исполнения | Таблица; столбчатая по ГП. Непилотные ГП (`CashExecution`) |
| 5 | Исполнение расходных обязательств в разрезе ГП (прил. 10) | `MfDataVolumeCashExecution`, `GRBS`, `VR`, `FKR` | Объём и кассовое исполнение по ГРБС и видам расходов | Таблица; **Маримекко** (2-я очередь) |
| 6 | Структура финансирования госпрограмм | `SubprogramFinancingValue`, `SubprogramActionFinancingValue`, `FCPFinancingValue`, `FinancingSource`, `GovernmentProgram` | Объём по источникам (федеральный бюджет, внебюджетные) | Круговая; **Маримекко** (2-я очередь) |
| 7 | Сводная статистика по госпрограммам | `GovProgramStatistic`, `FOIV` | Число подпрограмм, мероприятий, показателей, ФОИВ; объём расходов | Таблица; столбчатая |

Состав источников данных, доступных конструктору, определяется сущностями из этой таблицы и уточняется при необходимости. Подробнее — приложение Б.

> **Объём первой очереди.** Отчёты строятся по непилотным госпрограммам: в предоставленной модели данных нет сущностей пилотных программ.

### 7.1. Правила предметной области

Конструктор должен позволять выразить правила, по которым в системе строится сводный годовой доклад. Без них значения отчётов не совпадут с эталонными.

| Правило | Содержание |
|---|---|
| Версия программы | `GovernmentProgram` — версия, связей между версиями нет (их группирует `Gp`). Версия выбирается в фильтре; по умолчанию — выбранная версия программы |
| Выбор мониторинга | Берётся ежеквартальный мониторинг (`RealizationReport`) за 4-й квартал выбранного года, если его нет — за 3-й и далее. Программа без мониторингов за год в отчёт не попадает |
| Тип отчёта | `RealizationReport` включает годовые отчёты (`AnnualReport`) и «Доклады» (`RequestedReport`). Для сводных данных берутся годовые отчёты с флагом `IsIncludeInSummaryReport` |
| Счётчики контрольных событий | Запланировано — все КС. Выполнено — у КС есть `FactEndDate`. В срок — `FactEndDate` не позже планового срока (`ActualDate` в `PlanKeyEvent`). Позже срока = выполнено − в срок. Не выполнено = запланировано − выполнено |
| Значение с запасным | Для плановых и фактических значений берётся «скорректированное», а если оно пусто — исходное |
| Исключения в финансах | Из кассового исполнения исключаются строки межбюджетных трансфертов (ВР 550, 560, 570) и «иных расходов» (ВР 540 и ГРБС 392, 393, 394) |
| Строки факта без плана | `ReportKBKFinancing` может существовать для КБК без `KBKFinancing` (флаг `IsNew`); такие строки не теряются |
| Сортировка и группировка | Социально значимые направления — по возрастанию номера; в группах сводные значения; в конце строка «Всего» |

## 8. Требования к интерфейсу

Интерфейс полностью на **русском языке**: меню, подписи, сообщения об ошибках, форматы дат, чисел и валют, локализация компонентов Kendo UI (культура `ru-RU`). Внешний вид соответствует закрытой части АИС ГП (скриншоты из ВКР и руководства пользователя, часть 3).

**Компоновка**
- Модуль — раздел **«АНАЛИТИКА»** в главном горизонтальном меню (вкладки заглавными: ГОСПРОГРАММЫ, ВЦП, ПРОЕКТЫ, ПЛАНЫ, ОТЧЕТНОСТЬ, АНАЛИТИКА, АДМИНИСТРИРОВАНИЕ). Активная вкладка — белый фон, синий текст и подчёркивание; неактивные — серые.
- Справа в меню — имя пользователя и значок справки «?».
- Под меню — **панель инструментов (ribbon)**: кнопки со значком и подписью, сгруппированные по смыслу; подписи групп — серые, заглавными, под кнопками. Группа конструктора есть только у специалиста. Панель сворачивается стрелкой.

**Экран просмотра отчёта**
- Под панелью — выпадающие списки периода и госпрограммы (серые поля со стрелкой ▾).
- Слева — панель со списком отчётов (флажки) и перечнем госпрограмм; внизу кнопки «Выделить» и «Сформировать».
- Справа — область отчёта.

**Таблицы (Kendo Grid)**
- Серая шапка с многоуровневыми заголовками и строкой нумерации столбцов.
- Строки групп (госпрограмма, направление) — тёмно-серые, жирным, со сводными значениями; строка «Всего:» в конце.
- Числа и проценты по центру ячейки; проценты с одним знаком после запятой.
- Цветовая индикация долей: зелёный и жёлтый фон по порогам. Выделенная строка — синяя заливка.

**Кнопки и диалоги**
- Кнопки над таблицами — с контуром: синяя «+ Добавить строку», красная «Удалить выбранные».
- Модальные диалоги с кнопками «ОК» (синяя, с заливкой) и «Отмена» (с контуром); критичные действия подтверждаются диалогом.
- Вкладки внутри экрана — заглавными, активная подчёркнута (как «ПАСПОРТ»).
- Шрифт без засечек, светлая палитра, акцент — синий. Диаграммы в той же палитре.

## 9. Технические ограничения (стек)

- Платформа: **ASP.NET MVC 5, C#**.
- Архитектура: **Model-View-Controller**; отчётная логика — в сервисном слое, контроллеры тонкие.
- Представления: **Kendo UI**.
- Аутентификация: сессия АИС ГП, **без OAuth** и аналогов; в тестовом контуре — заглушка.
- Данные АИС ГП — по её модели (PostgreSQL); определения форм, настройки и личные представления — в собственной БД модуля.
- В системе: .NET 4.5, Entity Framework, представления `.aspx`. Модель в предоставленном виде — EDMX (типы PostgreSQL: `uuid`, `text`, `int4`), 315 таблиц, наследование «таблица на тип» (например, `Programs` + `Programs_GovernmentProgram`, `RealizationReports` + `RealizationReports_AnnualReport`). Запросы по наследникам содержат лишние соединения, поэтому отчёты выполняются только на чтение (`AsNoTracking`, при необходимости представления БД).
- Файл `GovProgramsModel.edmx.sql` — DDL под SQL Server от 2018 г.; для тестовой БД на PostgreSQL он не подходит, схема генерируется из `.edmx`.
- Все зависимости модуля должны быть совместимы с выбранной версией .NET Framework.

### 9.1. Хранилище модуля

Собственная БД модуля (PostgreSQL). Идентификаторы пользователей — `uuid` из АИС ГП (`USER_GUID`) без внешнего ключа, так как таблицы пользователей в модели нет.

| Таблица | Поля | Ограничения и индексы |
|---|---|---|
| `report_definition` | `id uuid` PK, `name`, `status` (`draft` / `published`), `definition jsonb` (источник, поля, группировки, формулы, фильтры, визуализация), `owner_id uuid`, `created_at`, `updated_at`, `row_version` | `name` не пустое; индекс по `status`; `row_version` для конфликта при одновременном редактировании |
| `user_view` | `id uuid` PK, `user_id uuid`, `report_id` FK → `report_definition`, `name`, `settings jsonb`, `created_at` | `UNIQUE (user_id, report_id, name)`; индекс по `(user_id, report_id)`; `ON DELETE CASCADE` по `report_id` |

Из этого следует: дубль имени представления отклоняется или заменяется по подтверждению; удаление формы удаляет личные представления; если после правки формы настройка представления ссылается на удалённый столбец, она игнорируется с сообщением.

### 9.2. Контракт API модуля

| Метод и адрес | Назначение | Доступ |
|---|---|---|
| `GET /reports` | Список форм (постраничный) | Пользователь: только опубликованные |
| `GET /reports/{id}` | Определение формы | Черновик — только специалист |
| `POST /reports`, `PUT /reports/{id}`, `DELETE /reports/{id}` | Создание, изменение, удаление | Специалист |
| `POST /reports/{id}/publish`, `.../unpublish` | Публикация и снятие | Специалист |
| `GET /reports/{id}/data?skip=&take=&sort=&filter=` | Данные отчёта; параметры, которые понимает Kendo Grid (серверная пагинация, сортировка, фильтры) | Пользователь |
| `GET/POST/PUT/DELETE /reports/{id}/views` | Личные представления | Владелец |

Правила: фильтры и сортировка принимаются только по полям из белого списка формы; статусы — 401 (нет входа), 403 (нет роли), 404 (нет формы или нет доступа к черновику), 409 (конфликт `row_version`), 422 (ошибка проверки формы, например недопустимая формула); тело ошибки — `{ "code", "message", "details": [] }`, сообщения на русском; изменяющие запросы защищены токеном от подделки запроса (`AntiForgeryToken` и для AJAX); JSON отдаётся объектом, а не массивом.

**Kendo UI.** Для модуля доступна лицензия, включающая:
- **Grid** — таблицы с группировкой, сортировкой, фильтрацией, итогами и многоуровневыми заголовками;
- **Chart** — столбчатые, линейные, круговые диаграммы и диаграммы с областями;
- **Drawing** — отрисовка кастомных элементов, в частности диаграммы Маримекко;
- русская локализация и тема оформления под стиль АИС ГП.

## 10. Допущения

- Ожидаемое число пользователей, одновременных сессий и объём данных намеренно не описываются; нагрузочные требования не предъявляются.
- Достаточно двух ролей («Специалист» и «Пользователь»); права на отдельные отчёты (по ведомствам и госпрограммам) не нужны.
- Сохранение пользователем личных фильтров и представлений требуется (п. 6.4).
- Диаграмма Маримекко реализуется во второй очереди, в первую версию не входит.
- Экспорт и печать отчётов не требуются.
- Передача пользователя и роли из АИС ГП определена моковым контрактом (п. 5.1); при подключении к реальной системе проверяется только адаптер.
- Перечень отчётов не фиксируется: формы создаёт специалист; разработка поставляет конструктор и тестовые примеры.

## 11. Критерии приёмки (общие)

- Неавторизованный пользователь не получает доступа к отчётам ни через интерфейс, ни по прямым ссылкам и API.
- Авторизованный пользователь открывает отчёт без повторного входа.
- Специалист создаёт и публикует табличный и графический отчёт без участия разработчика; после публикации форма автоматически заполняется данными тестовой базы.
- Черновик виден только специалисту.
- Пользователь не может создать или изменить форму, но настраивает и сохраняет своё представление.
- Весь интерфейс на русском языке и визуально соответствует АИС ГП.
- Отчёты, созданные в конструкторе на тестовых примерах из п. 7, формируются корректно, значения совпадают с контрольными расчётами по тестовой базе.
- Диаграмма Маримекко не входит в приёмку первой версии и принимается во второй очереди.
